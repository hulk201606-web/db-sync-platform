## 1. 项目定位与范围

### 1.1 一句话定位

面向**国产化替代与业务连续性**场景的异构数据库同步迁移平台：把数据从 Oracle/DB2/MySQL 迁到 DM8/PostgreSQL，做到**不停机、可验证、可回滚**。

### 1.2 解决的问题

传统迁移靠停机窗口 + DBA 手工脚本，三个硬伤：

| 痛点 | 后果 | 本平台的解法 |
|---|---|---|
| 8 亿行大表无法在窗口内迁完 | 只能停机数天 | 分片并行 + 断点续传 + 多实例抢占 |
| 迁完不知道数据对不对 | 差异在业务上线后才暴露 | 分块校验和比对 + 差异下钻 + 归一化治假阳性 |
| 切过去发现不对无法回退 | 事故不可逆 | 两段式状态 + Gate 卡点 + 灰度切流 + 回滚 |

### 1.3 范围内（五类数据源两两互通）

`MySQL` · `Oracle` · `PostgreSQL` · `DM8（达梦）` · `DB2`

互通方式：任意源 → 任意目标，**共 20 条组合**，由方言 SPI（`Dialect`）统一抽象，业务层代码不出现任何库专属 SQL。

### 1.4 范围外（本期明确不做）

- 不做跨库分布式事务（无 XA）——一致性靠「至少一次投递 + 幂等写入」
- 不做实时 CDC 日志解析（不接 Debezium/Canal，仅预留 `ChangeCaptureProvider` 接口）
- 不做数据清洗/ETL 转换编排（只做结构映射与类型转换）
- 不做双向同步（仅单向 + 可回滚）

## 3. 系统架构

### 3.1 模块划分（10 个 Maven 模块）

| 模块 | 职责 | 依赖约束 |
|---|---|---|
| `db-sync-common` | 领域模型、枚举、异常体系、工具、Options 对象 | 不出现 Spring 注解、不出现 JDBC |
| `db-sync-dialect` | 一切「库和库不一样」的东西：SQL 生成、元数据读取、触发器 DDL、能力声明 | 不做事务管理、不做业务编排 |
| `db-sync-metadata` | 元数据库自身：Flyway 脚本、18 表 DAO、`MetaJdbcTemplate` | 不操作业务库 |
| `db-sync-core` | 引擎零件：数据源注册表、流式读写、分片计划、checkpoint、租约、限速、线程池 | 只提供「怎么跑」，不决定「何时跑」 |
| `db-sync-migration` | 存量编排：预检 → 分片 → 抢占 → 读 → 写 → checkpoint → 核数 → 死信 | 不碰增量 |
| `db-sync-cdc` | 增量通道：变更入队 → 分组 → 保序消费 → 冲突策略 → 幂等 Upsert → 水位线 | 不碰存量分片 |
| `db-sync-compare` | 比对：分块校验和 → 差异下钻 → 归一化 → 修复 → 报告 | 不直接改路由 |
| `db-sync-cutover` | 灰度切流：状态机、路由规则、Gate、两段式状态、回滚 | 不直接读目标库（走 Port） |
| `db-sync-api` | REST、RBAC、审计切面、调度、指标注册 | 不含算法 |
| `db-sync-server` | `SpringBootApplication`、`application.yml`、Flyway 装配、静态资源 | 不含业务逻辑 |

### 3.2 依赖方向（单向，无环）

```
server → api → {migration, cdc, compare, cutover}
                    ↓
                  core → {dialect, metadata, common}
```

**关键约束**：`cutover` **不依赖** `cdc` / `compare`。它需要的「增量延迟 P95」和「比对通过率」通过 `core.port` 下的两个接口获取（`IncrementalMetricsPort` / `CompareVerdictPort`），由 `cdc` / `compare` 各自实现、在 `server` 层装配。好处：`cutover` 可单测（喂假 Port 即可），且避免模块环。

### 3.3 技术栈

Java 17 · Spring Boot 3.2.11 · 原生 JDBC（无 ORM）· Flyway · H2（测试/demo）· MySQL 8.0（生产元数据库）· Prometheus（可选）

**为什么不用 ORM**：迁移引擎要控制 `fetchSize`、`autoCommit`、批量绑定、游标语义，这些在 JPA/MyBatis 下会被框架包住，反而失真。

## 5. 五条核心链路

### 5.1 存量迁移

```
预检 → 生成分片 → [循环] 抢占分片(租约30s) → 流式读 → 批量写(幂等)
     → 事务提交 → 推进 checkpoint → 释放/续租
     → 分片 SUCCESS → 全部终态 → 核数 → FINISHED
```

**不变式 I1（最重要）**：`CheckpointStore.save()` 只能在批次事务 `commit()` 成功之后调用。写反了不会报错，但宕机恢复会跳过未提交的数据——**静默丢数据**。

### 5.2 增量消费

```
源变更 → 日志表/双写入队(seq 单调) → 按主键哈希分组(16组)
      → 组内串行消费 → 冲突策略裁决 → 幂等 Upsert → 推进水位线
      → 失败重试3次 → 死信
```

**不变式 I4**：水位线 = `MIN(未应用 seq) - 1`。若用 `MAX(已应用)`，组间乱序完成时会跨过未应用的空洞，**那部分变更永久不再消费**。

### 5.3 全量比对

```
分块(10万行) → 块级 COUNT → 不一致则 SUM → 再不一致拉块内行
           → 逐行归一化后比对 → 差异落 sync_compare_diff → 汇总结论
```

**不变式 K4**：`Normalizer` 必须全局单实例注入。两份实现 = 两套归一化 = 报告互不相信。

### 5.4 灰度切流

> **以代码枚举 `CutoverState`（9 状态）为唯一真源**。v1.1 之前的本文档与前端曾沿用设计稿的
> `SHADOW / FULL_WRITE / FULL_READ` 八状态口径，与实现不符，v1.2 已按枚举全文校正（见 §15.4）。

```
DRAFT → PRE_CHECK ──失败──→ PRE_CHECK_FAILED ──重检──→ PRE_CHECK
              │ 通过
              ↓
        GRAY_READ(读灰度) → GRAY_WRITE(写灰度/双写)
              → FULL_TARGET(全量目标) → OBSERVE(观察期) → DONE(终态)
                                    │
                    非终态异常 ─────┴──→ ROLLED_BACK(已回滚，终态)
```

前进跃迁由 `CutoverState.forwardTargets()` 定义：`PRE_CHECK → {GRAY_READ, PRE_CHECK_FAILED}`、
`GRAY_READ → GRAY_WRITE`、`GRAY_WRITE → FULL_TARGET`、`FULL_TARGET → {OBSERVE, DONE}`、
`OBSERVE → DONE`；`DONE / ROLLED_BACK` 为终态。**不存在** `INCONSISTENT` 状态。

每步推进前由 `GateEvaluator` 判定 4 个卡点，不达标拒绝推进（`E6002`）。

### 5.5 结构映射

```
读源表元数据 → 类型映射 → 标识符策略 → 生成 DDL → 风险扫描 → 人工覆盖(可选) → 固化映射
```

> **大盘设计说明**：只暴露一个聚合接口 `/api/monitor/overview`，不拆 `tps`/`shards`/`tables` 多个端点。原因是大盘按 5s 轮询，4 个接口 = 4 倍请求与 4 次不一致的快照；单接口保证同一时刻一致视图。

## 8. 状态机全集

### 8.1 同步任务

`DRAFT → READY → RUNNING ⇄ PAUSED → FINISHED / FAILED → ARCHIVED`

| 操作 | 允许的当前状态 | 拒绝码 |
|---|---|---|
| start | READY | E3001 |
| pause | RUNNING | E3001 |
| resume | PAUSED | E3001 |
| cancel | RUNNING, PAUSED | E3001 |
| rerun(fromCheckpoint) | FAILED, FINISHED | E3001（FINISHED 重头需 ADMIN） |
| archive | FINISHED, PAUSED, DRAFT | E3001 |

### 8.2 分片

`PENDING → CLAIMED → RUNNING → SUCCESS / FAILED / PAUSED`
`FAILED → PENDING`（重试未耗尽）→ `DEAD`（耗尽）→ `PENDING`（人工重放）
`RUNNING/CLAIMED → PENDING`（**租约过期**，这是「进程宕机」的唯一表达）

> 注意：`LeaseReaperJob` 与 `claim` 必须使用**同一个**判据 `lease_expire_at < now(3)`，否则出现「reaper 认为该回收、claim 认为不能抢」的死区。

### 8.3 切流（9 状态）

以 `CutoverState` 枚举为准：`DRAFT / PRE_CHECK / PRE_CHECK_FAILED / GRAY_READ / GRAY_WRITE / FULL_TARGET / OBSERVE / DONE / ROLLED_BACK`。
主干为 `DRAFT → PRE_CHECK → GRAY_READ → GRAY_WRITE → FULL_TARGET → OBSERVE → DONE`；预检失败进 `PRE_CHECK_FAILED`（可重检回 `PRE_CHECK`），非终态异常可 `ROLLBACK → ROLLED_BACK`。
`DONE / ROLLED_BACK` 为终态；**无** `SHADOW / FULL_WRITE / FULL_READ / INCONSISTENT`（这些是早期设计稿口径，见 §5.4 与 §15.4）。
前端 `Cutover.tsx` 的 `FLOW`、`NEXT_LABEL`、`format.ts` 的中文表、`types/index.ts` 的联合类型自 v1.2 起统一按此 9 状态生成，不再出现按钮文案 `undefined`。

### 8.4 比对作业

`PENDING → RUNNING → DONE / FAILED / CANCELED`。`DONE` 不可重跑（结论会被 Gate 引用，重跑会使「结论与执行时间不符」），要重跑就新建 job。

## 9. 错误码体系

| 段位 | 范围 | 归属 | 示例 |
|---|---|---|---|
| E1xxx | 1000-1999 | 通用/参数/工具 | E1001 参数非法、E1002 标识符非法、E1010 加解密失败 |
| E2xxx | 2000-2999 | 数据源/连接/池 | E2001 认证失败、E2002 网络失败、E2003 被引用、E2010 池超限 |
| E3xxx | 3000-3999 | 任务/迁移/分片 | E3001 非法状态、E3002 预检失败、E3005 乐观锁冲突 |
| E4xxx | 4000-4999 | 增量/CDC | E4002 水位线回退、E4003 触发器部署失败、E4010 变更应用失败 |
| E5xxx | 5000-5999 | 比对/修复 | E5001 分块失败、E5003 修复证据不足 |
| E6xxx | 6000-6999 | 切流/Gate | E6001 非法跃迁、E6002 Gate 阻断、E6004 状态不一致 |
| E7xxx | 7000-7999 | 驱动/方言/环境 | E7001 驱动缺失、E7002 方言不支持、E7003 标识符超长 |

每个错误码含 `code / httpStatus / retryable / messageTemplate`；`retryable=true` 才会被 `RetryTemplate` 重试。

## 10. 配置项

> **以 `db-sync-server/src/main/resources/application.yml` 为准**。注意有**两个前缀、两套装配**，不要混写：
> - `dbsync.*`：主配置，由 `DbSyncProperties`（`@ConfigurationProperties(prefix = "dbsync")`）绑定；
> - `db-sync.meta.*`：**仅元数据库连接**，由 `db-sync-metadata` 的 `MetaDataSourceConfig` 独立装配。
>
> v1.0 本节曾列 `migration.default-concurrency` / `compare.block-rows` / `cutover.gate.*` / `observability.prometheus-enabled` 等键，
> 它们来自架构设计稿，**并未落到 `application.yml`**；对应行为由代码默认值或任务级字段（如 `sync_task.consumer_concurrency`）决定。

  auth:

| 键 | 默认值 | 用途 |
|---|---|---|
| `dbsync.cdc.poll-interval-ms` | `5000` | 采集默认周期；**任务级 `sync_task.poll_interval_ms` 优先** |
| `dbsync.jobs.cdc-reconcile-ms` | `30000` | 消费会话周期对账（`@Scheduled` 占位符） |

> **覆盖口径（v1.2 更正）**：带 `${DBSYNC_*}` 占位符的键可直接用同名环境变量覆盖；
> `dbsync.alert.channels` 用 `DBSYNC_ALERT_CHANNELS`（逗号分隔）覆盖；`dbsync.cdc.*` 与
> `dbsync.jobs.cdc-reconcile-ms` 等只在代码里给默认值的键，写 yaml 同名键即可覆盖。
> v1.1 的「全部键都可用 `DBSYNC_*` 覆盖」不成立。
>
> §10 此前漏记的在用键（v1.2 补齐）：`dbsync.cdc.batch-size`（默认 500）、`dbsync.report-dir`（默认 `reports`）、
> `db-sync.meta.pool-max-size` / `pool-min-idle`（默认 10 / 2）、`dbsync.cors.allowed-origins`
> （环境变量 `DBSYNC_CORS_ALLOWED_ORIGINS`，默认仅 localhost/127.0.0.1）、
> `spring.task.scheduling.pool.size`（默认 **6**，与 6 个 `@Scheduled` 入口一一对应）、
> `dbsync.jobs.token-cleanup-ms`（默认 60000）。
> 仍为**代码内硬编码、不可配**的常量：`HealthProbeJob` 的探活线程池 4 线程、单源 8s / 整轮 60s 时限，
> 以及 `CdcRuntimeConfig` 的 200ms 采集空转间隔。新增 `@Scheduled` 入口时必须同步调大池大小。
> `dbsync.claim-strategy` 为唯一抢占策略真源，`db-sync.meta.claim-strategy` 已不再由 DAO 独立绑定。
> 设计层完整清单见 `docs/02-architecture.md` §10，**实现一律以代码为准**。

## 11. 运行与部署

### 11.1 环境要求

| 项 | 版本 |
|---|---|
| JDK | 17+ |
| Maven | 3.6.3+ |
| MySQL（元数据库，生产） | 8.0+（需 `SKIP LOCKED`） |
| H2（测试/demo） | 2.x，无需安装 |

### 11.2 本地启动

```bash
cd D:/GC_WorkSpaces/db-sync-platform

# 1) 编译（首次会下载依赖）
mvn clean install -DskipTests

# 2) 以 h2 档启动（内存元数据库 + 演示主密钥，无需外部 MySQL）
cd db-sync-server && mvn spring-boot:run -Dspring-boot.run.profiles=h2
```

- 端口 `8080`，无 context-path。
- **不要用 `mvn -pl db-sync-server -am spring-boot:run`**：父 POM 继承该插件，`-am` 会让聚合根也执行 `run` 目标并因「找不到 main class」直接失败。必须在 `db-sync-server` 目录内启动（依赖先用 `mvn install` 装进本地仓库）。
- 默认账号：**`admin` / `Admin@12345`**（`V2__seed.sql` 种子数据，生产必须改）。
- 健康检查：`GET http://localhost:8080/actuator/health`
- 注意：**不带 `h2` 档启动会失败**——默认档的 `dbsync.master-key` 只从环境变量 `DBSYNC_MASTER_KEY` 读取，留空即拒绝启动（有意设计：密钥绝不进代码库）。

### 11.3 配置档说明

| 档 | 元数据库 | 主密钥 | 用途 |
|---|---|---|---|
| 默认 | **H2 文件库** `jdbc:h2:file:./data/meta`（`DBSYNC_META_URL` 缺省值） | 必须环境变量注入（≥32 字符，启动强校验） | 单机开发 / 联调 / 演示 |
| `h2` | H2 内存库 + 自动 Flyway | 内置演示值 | 本地开发、演示、测试 |

> **生产前提（v1.2 更正）**：默认档是本地 H2 **文件**库，不支持多进程/多机共享；生产**必须**显式设置
> `DBSYNC_META_URL` 指向共享 MySQL 8，否则多实例各写各的元数据、换机/重启即丢库。
> `MetaDataSourceConfig` 的 `@Value` 兜底值已与默认档对齐，**不再**静默兜底到 `jdbc:h2:mem`。
> v1.1 曾把默认档写成「MySQL」，属文档失真。

生产环境变量清单：`DBSYNC_MASTER_KEY`（≥32 字符）、`DBSYNC_META_URL`、`DBSYNC_META_USER`、`DBSYNC_META_PASSWORD`、`DBSYNC_PORT`、
`DBSYNC_ALERT_CHANNELS`（默认 `LOG`；需 WEBHOOK/EMAIL 时写 `LOG,EMAIL,WEBHOOK`）、`DBSYNC_ALERT_WEBHOOK`、
`DBSYNC_ALERT_MAIL_ENABLED` / `_HOST` / `_PORT` / `_USERNAME` / `_PASSWORD` / `_FROM` / `_STARTTLS` / `_SSL` / `_CONNECT_TIMEOUT_MS` / `_RECIPIENTS`。

> **告警是两层开关**：`channels` 是渠道总开关（默认仅 `LOG`，会把规则里的 WEBHOOK/EMAIL 全部过滤），
> `mail.enabled`（默认 `false`）是第二层；两层同时打开且 `host/from/recipients` 齐全才会真正发信。
> 启动时 INFO 打印生效渠道，配置不全时 WARN —— 不再「配了却不发且毫无提示」。

### 11.4 驱动说明（重要）

Oracle / DM8 / DB2 驱动**不在 pom 中**（授权问题，且会让所有人 `mvn test` 失败）。使用方式：

1. 将驱动 jar 放入 `lib/` 目录（或加入 Maven `-Dmaven.repo.local` 私有仓）
2. 启动时用 `-Dloader.path=lib/` 或 `--spring.jdbc.driver-class-name`
3. 代码通过 `Class.forName(driverClassName)` 反射加载，缺失时抛 `E7001`

CI 有一条硬检查：`pom.xml` 里出现 `ojdbc` / `DmJdbc` / `jcc` 即失败。

### 11.5 前端构建产物与 SPA 路由

```bash
cd db-sync-console
npm install
npm run build         # 仅产出 db-sync-console/dist（本地预览用）
npm run build:server  # 产出并直接写入 db-sync-server/src/main/resources/static（交付用）
```

- `npm run build:server` 带 `--emptyOutDir`，会**清空并覆盖**后端静态目录（含默认占位页），因此不要在两个地方各放一份 `index.html`。
- Vite `base` 必须为 `/`：相对 base 会让 `/compare/:id` 这类二级路由把 assets 解析到 `/compare/assets/*` 并 404。
- **SPA 回落**：`SpaFallbackFilter` 将「GET/HEAD + 无扩展名 + 不以 `/api`、`/actuator`、`/h2-console` 开头」的请求 forward 到 `/index.html`。因此刷新 `/monitor`、`/compare/123` 不会 404，而 `/api/not-exists` 仍返回 404（不被 HTML 吞掉）。
- 前提：`classpath:/static/index.html` 必须存在。顺序是「先 build:server，再启动服务」。

## 13. 风险与限制

### 13.1 高危风险（Top 6）

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | DM8 驱动/实例不可得 | M1 无法验收，DM 适配后置导致返工 | 第 1 周要求实例就绪；方言层单测不依赖实例 |
| R2 | Oracle 大表读取 OOM | 8 亿行表必崩 | 强制 `autoCommit=false` + `fetchSize`，并有单测断言 |
| R5 | 比对假阳性 | 报告不可信 → 产品价值归零 | 单一 Normalizer + 注入差异测试集门禁（误报率 ≤ 0.1%） |
| R6 | 增量乱序旧值覆盖新值 | 目标数据错乱 | `groupCount` 只读 + 分组串行 + 端到端「同一主键 1000 次递增」测试 |
| R7 | 切流状态与路由不一致 | 可能丢数据 | 两段式状态 + `route_version` 单调 + 启动对齐 |
| R9 | Oracle `NUMBER` 无精度截断 | 国产化替代最常见生产事故 | 预检跑 `MAX(LENGTH(TO_CHAR(col)))` 出报告，超限清单交客户确认 |

其余 R3/R4/R8/R10~R13 见 `docs/02-architecture.md` §14。

### 13.2 本期已知限制

| 限制 | 说明 |
|---|---|
| 无主键表 | 只支持表级重跑，不支持精确断点（需客户书面接受） |
| 增量保序 | 仅触发器模式保证强序；时间戳模式靠 `(ts,version)` 去重，弱序 |

## 附录 B：关键决策记录（ADR-lite）

> 记录会对交付范围产生实质影响的决策，含被推翻的决策，便于后续追溯「当初为什么这样」。

| # | 决策 | 结论 | 理由 / 影响 |
|---|---|---|---|
| D1 | 迁移链路是否用 ORM | **不用**，全原生 JDBC | 需精确控制 `fetchSize` / `autoCommit` / 批量绑定 / 游标语义，ORM 会包住这些 |
| D2 | 方言如何隔离 | `Dialect` SPI + 5 实现，业务层零库专属 SQL | 20 条互通组合，若散落 if-else 必然失控 |
| D3 | Oracle/DM/DB2 驱动是否入 pom | **不入**，反射加载 | 授权问题；入 pom 会让所有人 `mvn test` 失败（R11） |
| D4 | 一致性模型 | at-least-once + 幂等写 = 逻辑 exactly-once | 不做 XA，跨库分布式事务成本远高于收益 |
| D5 | 只读窗口 | 按 **≤ 5 分钟** 设计，不做 `DRAIN` 分支 | 零窗口需 +2 周且业界极少真正零窗口；状态机预留扩展点 |
| D6 | Oracle 无精度 `NUMBER` | 默认 `numeric(38,10)` + `PRECISION_LOSS` 风险标注 | 无实测分布时的最保守可用默认；列为 R9，上线前必须跑统计 |
| D7 | ~~前端只交付静态只读页~~ | **已推翻**：交付 React 控制台（10 路由） | 原 Q-A 决策为省 15~20 PD；用户追加需求后改为完整交付，见 §12 |
| D8 | 前端是否用 MUI + Tailwind | **不用**，改设计令牌 + 自研组件 | PRD 原定 MUI+Tailwind；两套样式体系互相污染、体积翻倍，手写 CSS 可覆盖全部线框 |
| D9 | 大盘接口拆分粒度 | 单接口 `/api/monitor/overview` | 5s 轮询下拆 4 个接口 = 4 倍请求 + 4 个不一致快照 |
| D10 | 比对作业 `DONE` 后是否可重跑 | **不可**，只能新建 job | 结论被 Gate 引用，重跑会造成「结论与执行时间不符」 |
| D11 | 无主键表 | 只支持表级重跑，无精确断点 | 无主键无法构造稳定区间游标（需客户书面接受） |
| D12 | `groupCount` 是否可运行时调整 | **不可**，创建后只读 | 变更会破坏「组内保序」，导致旧值覆盖新值（R6） |
| D13 | 增量消费何时装配 | **按任务运行期装配**，不做单例 Bean | 任务删/暂停后必须能停；`CdcRuntimeManager` + `ApplicationReadyEvent` 恢复 + 30s 对账 |
| D14 | 采集与消费谁启动 | **同一 manager 成对启停**：start 先采集后消费，stop 先停采集再停消费 | 否则暂停后队列还在长，或采了没人消费 |
| D15 | 冲突策略是否持久化 | **按表可配**（V3 加列 + 写入口） | 工厂原写死 `SOURCE_WINS` 等于该需求未达成；非法值 `E1001` fail-fast，不静默兜底 |
| D16 | 多实例采集防重 | 位点行当**每表租约**（`claimIfIdle` 原子认领），唯一约束留待后续 | 加 `(task_id,mapping_id,seq)` 唯一约束属建表变更；租约下重复采集只多花 IO，upsert 幂等不改正确性 |
| D17 | 运行中改限速如何生效 | `ThrottleRegistry` 按 taskId 缓存，**API 与 worker 用同一实例** | `MigrationEngine.Session` 原本不持有 Throttle；不建注册表会「改了一个对象、跑的是另一个」 |
| D18 | SDK 补偿表放哪 | **业务侧数据库**（`sync_sdk_outbox`），不放平台元数据库 | 元数据库不可达时业务方仍需能落补偿；建表走 `Dialect.createTableDdl`，不写死 MySQL |
| D19 | 路由快照如何下发 | 平台只读端点 + SDK 后台轮询（TTL 3s），不推消息 | 无消息中间件；版本只增不减，hash 复用平台 `HashUtil.fnv1a64` 保证灰度比例一致 |
| D20 | 邮件告警失败是否抛 | **永不抛**：未配置/发送失败返回 `false` + 日志，与 Webhook 共用静默去重 | 一个 SMTP 故障不能打断整条告警链路 |
| D21 | 新增依赖 | 允许 `spring-boot-starter-mail`（Boot 官方 starter） | 邮件能力必需；未引入任何第三方邮件库，依赖白名单变更留痕 |
| D22 | 非唯一索引 DDL 在哪生成 | 修复 `AbstractDialect.createIndexDdl`（**唯一实现，无任何方言 override**），移除 `indexInlineInCreateTable()` 开关 | 原 MySQL 走该开关会让整个方法返回空，而 `CREATE TABLE` 只内联唯一键 → 非唯一索引被静默丢弃，MAP-03 不达标且 MAP-05 全误标 `MISSING`。**实际影响全部 5 种方言**（都改为按需发 `CREATE INDEX`），既有方言测试按新行为修订断言 |

### 17.6 真实库 E2E 补跑与 Flyway 方言缺陷（2026-11-10）

§17.5 曾把真库 E2E 记为「入口已提供、本轮未执行」，原因是 Docker Hub 鉴权端点被网络阻断。2026-11-10 用镜像加速器补齐基础镜像后完成补跑，并抓到一个 **P0 级启动缺陷**。

**镜像链路**：`auth.docker.io` / `registry-1.docker.io` 均不可达（HTTP 000），`docker.m.daocloud.io` / 阿里云 ACR / quay / ghcr 可达（HTTP 401）。从 `docker.m.daocloud.io/library/` 拉取 `maven:3.9-eclipse-temurin-17` 与 `eclipse-temurin:17-jre` 后 `docker tag` 回官方名，**`Dockerfile` 与 `docker-compose.yml` 零改动**；三个业务镜像 `mysql:8.0` / `postgres:16-alpine` / `mailhog` 本地已有。

**环境**：MySQL **8.0.46**（宿主 3307）、PostgreSQL **16.15**（5433）、MailHog v1.0.1（1025/8025）、app（8080），四个容器全部 healthy。

**首跑失败（H2 全绿也发现不了的缺陷）**：

```text
HikariPool - dbsync-meta - Added connection com.mysql.cj.jdbc.ConnectionImpl   ← 驱动与连接均正常
org.flywaydb.core.api.FlywayException: Unsupported Database: MySQL 8.0          ← Flyway 方言缺失
```

根因：Flyway **9.22.3 的 `flyway-core` 只内置 h2 / postgresql / db2 / oracle 等方言，MySQL 方言拆在独立 artifact `flyway-mysql`**。项目 737 个测试全部跑在 H2 上，因此从未暴露；而 §11.3 明确要求生产用 MySQL 8 元数据库——按原样部署会 100% 启动失败。

修复（`db-sync-metadata/pom.xml`，Java 代码零改动）：

```xml
<dependency>
  <groupId>org.flywaydb</groupId>
  <artifactId>flyway-mysql</artifactId>
  <version>${flyway.version}</version>
</dependency>
```

**验证结果**：

|---|---|
| 全量回归 | 737 次执行 / 0 failures / 0 errors / 0 skipped，10 模块 BUILD SUCCESS |
| `./scripts/smoke-real-db.sh` | `PASS`：health UP、Flyway 4 成功 0 失败、登录取令牌、`/api/openapi.json` HTTP 200 |
| Flyway 记录 | V1 init / V2 seed / V3 mapping conflict policy / V4 sdk route ack，`success=1` 全通过，`now at version v4` |
| 实建表 | `dbsync_meta` **19 张** = 18 张元数据表 + `flyway_schema_history` |

**MySQL → PostgreSQL 全链路补跑（同日）**：在真实 MySQL 8.0.46 源库与 PostgreSQL 16.15 目标库上跑通 `migrate → compare → cutover`，并在此过程中修掉 3 个只有真库才暴露的 P0 缺陷：

| # | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| 1 | MySQL 源库映射生成读到**实例内所有库**的表（`cutover_plan` 等元数据表被当成业务表） | `JdbcMetadataReader` 把 schema 传给 `DatabaseMetaData.getTables` 的 **catalog 位**且默认传 `null`，MySQL 驱动视作「不限制」 | 抽出 `catalogOf(c, schema)` / `schemaPatternOf(c, schema)` 钩子；`MySqlMetadataReader` 覆盖为「库名走 catalog、schemaPattern 恒 null」，非真实 MySQL 驱动（H2 模拟）回退父类行为 |
| 2 | 切流 `advance` 在 `FULL_TARGET` 报 `FULL_TARGET → FULL_TARGET` 非法跃迁，卡在倒数第二步 | `CutoverStateMachine.nextForward` 对多分支状态返回 `null`，而 `FULL_TARGET` 有 `{OBSERVE, DONE}` 两个出口 | 多分支时默认返回 `OBSERVE`（不可跳步，`DONE` 必须由观察期再推一步） |
| 3 | SDK 永远 ack 不到目标版本，每次 `advance` 都 `CONFIRM_TIMEOUT` 回退 | `/api/sdk/route-snapshot` 返回 **confirmed** 版本（推进中恒为 0），而编排器等的是 **intent**（最新发布）版本 | 快照优先返回内存 `RouteRegistry.current()` 的版本与 intent 状态，ack 后才写 confirmed |

**全链路实测**：源表 20 行 / SUM 21006.05 → PG 建表（`NUMERIC(12,2)` / `TIMESTAMP(3)` / 双引号标识符）→ 迁移后 20 行 / SUM 一致 → 比对 `verdict=PASS, totalRows=20, diffRows=0, passRate=1.0` → 切流 6 步全 SUCCESS：`DRAFT → PRE_CHECK → GRAY_READ → GRAY_WRITE → FULL_TARGET → OBSERVE → DONE`，最终快照 `readFrom=TARGET / writeTo=TARGET / grayRatio=100`，`routeVersion=6`，每步 ack 往返约 700ms。

**改密审计补齐**：`POST /api/auth/password` 此前缺 `@Audited`（管理员重置有），导致「谁改了密码」查不到。已补 `@Audited(action="USER_CHANGE_PASSWORD", targetType="USER")`，真库实测 `sys_audit_log` 落 `USER_CHANGE_PASSWORD / admin / USER / SUCCESS`；新增 `ChangePasswordAuditTest` 锁定该契约。

**回归基线**：本轮修复后 `mvn -B clean test` = **741 次执行 / 0 failures / 0 errors / 0 skipped**（737 + `MySqlMetadataReaderTest` 3 条 + `ChangePasswordAuditTest` 1 条）。

**仍未验**：DM8 / Oracle / DB2 真连（无实例，只能挂 `⬜`）、PG 之外的方言全链路、客户自有 SMTP 服务器、4 实例并发与压测。逐条判定见 `docs/05-milestone-acceptance.md` §3.2 与 §9。

**教训**：① **H2 全绿不等于生产可用**——方言、驱动、连接串这类「环境相关」缺陷只能由真实库暴露；② 每新增一种元数据库类型，必须同时补齐对应的 Flyway 方言模块，并加一条「真实库启动」用例，否则测试基线再高也挡不住；③ 镜像站地址不要硬编码进 `Dockerfile`，用本地 tag 或构建参数注入，避免污染交付物。
